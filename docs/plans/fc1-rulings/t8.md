# FC1 Task 8 — Spike: slatedb as the keyed-state backend (report, 2026-10-29)

Spike code: branch `fc1-t8-slatedb-spike` in `ostrium-labs/streamfusion` (`spikes/slatedb-state`, never merged). slatedb 0.17.0 (2026-09-29) against `rust-rocksdb` 0.22, the version the engine uses.

**Setup.** 200,000 keys spread over 128 key groups, each key a 2-byte key group followed by a u64; 64-byte values. One database stands in for one subtask. The object store is the local file system (`LocalFileSystem`), not S3. The laptop was loaded (load average about 15–25) while other lanes built, so every number is an indication (estimate), not a benchmark.

| | slatedb 0.17.0 | RocksDB |
|---|---|---|
| Sequential puts | 5.2 s (38,000 puts/s), each awaited separately with no batching | 0.52 s (388,000 puts/s) |
| Flush | 0.8 ms | 91 ms |
| Point gets, warm (p50 / p99) | 4 µs / 8 µs | 1 µs / 3 µs |
| Checkpoint | 268 ms, a manifest pointer with no data copied | 15 ms local, plus copying 15.6 MB out (1 ms to local disk; an S3 upload would dominate) |
| Rescale: a new subtask takes key groups 0–63 | **4.4 ms**: a clone from the checkpoint with a projection range, zero-copy; scanning the clone took 380 ms for 100,000 keys | 386 ms: scan the restored checkpoint and write the range into a new database |

**Findings**
- **Rescaling.** slatedb's clone with a projection range (`CloneSourceSpec::with_projection_range`, several sources allowed) is what key-group rescaling needs. A new subtask's state becomes a manifest operation, not a copy.
- **Checkpoints.** They are manifest pointers, so incremental checkpoints upload nothing beyond what is already flushed.
- **Write and read paths.** These are slower in this naive form: every put is awaited, and there is no write batch and no foyer cache in front. Batching (`WriteBatch`) and the block cache are the obvious next steps.

**Ruling (R8.1, D2252 and Q1440 unchanged):** RocksDB, ported from StreamFusion, stays FC1's keyed-state backend. slatedb is re-measured in FC2 on S3 (RustFS, then AWS) with batched writes and the foyer cache. It becomes the default only if its write and read throughput per core is within 2× of RocksDB with incremental uploads to S3 (estimate bar), because its rescale and checkpoint properties are clearly better.
