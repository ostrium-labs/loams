| R14.5 | **Parameterised views are called as table functions** (gap 1). The read plan expands the call as a view: a parameterised body is explained with each `{name:Type}` as `defaultValueOfTypeName('Type')` (ClickHouse explains nothing with a parameter unset, `456`), and views are made deepest first, so a view two others read exists before either (a plain view is analysed at creation; a parameterised one is not) | Laminar's migrations 4, 8, 10, 13, 15, 26, 36, 49; measured on 26.9.2.8 | Low: a `{name:Identifier}` parameter does not explain, so such a view is refused, not misread. | R14.9 | **`EXCHANGE TABLES a AND b` is three catalog renames** (gap 7a): `a` → a name of the House's own (`__loams_exchange_…`), `b` → `a`, that → `b`, undone in reverse when a step fails. Iceberg REST has no swap, so it is **not atomic** as ClickHouse's is: a statement resolving `a` or `b` between the steps can get `60`, and a front that dies between them leaves the moved table under the House's name (not listed). `EXCHANGE DICTIONARIES` is `48` | Laminar's 35, 48 and its frontend's cluster rebuild | Medium if a writer uses it under load; Laminar uses it in migrations and once at start |
| R14.10 | **No Iceberg bounds for `uuid` columns.** ClickHouse 26.9's Iceberg reader misreads a `uuid` column's bounds and prunes every file an equality should read: on clickhouse-server 26.9.2.8, `icebergLocal` over a House table answers `WHERE project_id = toUUID(…)` with 0 rows, and 3 with `use_iceberg_partition_pruning = 0`. The write path writes no Parquet statistics for `uuid` columns, so no bounds; files written before keep theirs until compaction rewrites them. Not reported upstream (owner's call) | Found running Laminar: every Laminar read filters by a `UUID` `project_id` | Low: `uuid` columns are not pruned by bounds |
| R14.11 | **SQL functions are the namespace's** (gap 7b). `CREATE [OR REPLACE] FUNCTION [IF NOT EXISTS]` and `DROP FUNCTION` keep a function as a file-less catalog entry in the House's own `__loams_functions`; a built-in's name is `609`, dropping one `610`, an unknown one `46`, as ClickHouse answers. The lambda is held to the deny list when made and again when used. A statement that calls one (directly, in a view, or in another function) gets it made on its worker's control connection before its views (`CREATE OR REPLACE FUNCTION`), and the worker drops every SQL function before its next statement. The worker's `default` gains `CREATE`/`DROP FUNCTION`, which the user connection's `readonly` keeps from it (a test on both engines) | Laminar's 66 (`apply_pii_masks`, `trace_visible`); `review:greptile` (security) | Medium: a new grant on the control connection |
| R14.12 | **Dictionaries read the namespace's tables** (gap 5). `CREATE [OR REPLACE] DICTIONARY` keeps a file-less catalog entry (as a view) with its attributes, key and the `SELECT` its rows come from: `SOURCE(CLICKHOUSE(TABLE | QUERY [DB] [WHERE]))` only. `USER`/`PASSWORD` are read and **not kept** (the dictionary reads with the identity of the statement that reads it); `HOST`, `PORT`, `SECURE` and every other source are `344`; range, IP-trie, polygon, regexp layouts, `HIERARCHICAL`, `DEFAULT` and `EXPRESSION` attributes are `48`. **Every layout is read directly**: a statement whose `dictGet…`/`dictHas` names one gets a view of its rows over the statement's pinned tables and a `DIRECT` (or `COMPLEX_KEY_DIRECT`) dictionary over that view, so it answers the same keys from the statement's snapshot (a cache's `LIFETIME` can only be staler). The worker's `default` gains `CREATE`/`DROP DICTIONARY` (not in `system`) and `dictGet`; its control DDL takes only that dictionary shape | Laminar's 43, 45, its views' `dictGet`, and the four dictionaries its frontend makes at start; `review:greptile` (security) | Medium: a lookup reads its source per block, no cache |
