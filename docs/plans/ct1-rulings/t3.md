# CT1 Task 3 — `loams-transport`: identity and the CA service (rulings)

## Part 1 (2026-10-29): identities, mTLS configurations, peer identity

This part adds the new crate `crates/loams-transport` (`publish = false`). Nothing in the product uses it yet.

- `SpiffeId` parses and formats the D2308 IDs: `spiffe://<cluster>/<node|role|svc>/<name>`.
  - It follows SPIFFE's trust-domain and segment character rules, with a maximum length of 2048 bytes.
  - It uses exactly two path segments.
  - `short()` (`role/gateway`) is the form route policies will name (Task 4).
- `tls::server_config` and `tls::client_config`:
  - TLS 1.3 only, with aws-lc-rs as an **explicit** provider (`builder_with_provider`), so the configs do not depend on any process-wide default provider;
  - client certificates are required on the server side (`WebPkiClientVerifier`);
  - one ALPN per config (`h3` or `h2`);
  - `max_early_data_size = 0` on the server and `enable_early_data = false` on the client (D2318).
- `peer::peer_identity` reads every SPIFFE URI SAN from a verified leaf, so a node certificate can carry `node/` plus its `role/` IDs. It refuses a certificate whose IDs name more than one cluster.

**R3.1 Crypto provider split.** `crates/loams` builds its existing TLS (the House link and the main-port TLS of `tls.rs`) on **ring** (`rustls` `ring` feature, `tokio-rustls` `ring`). `loams-transport` uses **aws-lc-rs** (D2306).
- Both providers can live in one binary because each config names its provider explicitly.
- Moving `crates/loams`' own TLS to aws-lc-rs is a separate change for T1 (Task 6), done when the cluster listener moves onto `loams-transport`. It is not done here.

Tests (`cargo test -p loams-transport`, 8 in total):
- `round_trips_every_kind` and `refuses_what_is_not_an_identity`;
- in-memory handshakes (no sockets), for `h3` and `h2`: `mutual_tls_names_the_peer_on_both_sides`, `a_client_from_another_ca_is_refused`, `a_client_without_a_certificate_is_refused`;
- `a_certificate_without_a_spiffe_id_has_no_identity`, which also refuses mixed clusters;
- `zero_rtt_is_off_on_both_sides` and `an_empty_bundle_is_an_error`.

Clippy passes with `-D warnings`. Buck is regenerated.

- `loams ca init|status|token|revoke|rotate`.
- The deny list.

## Part 2a (2026-10-30): the CA, join tokens, identities and the deny list

This part is still library code. Nothing in the product uses it yet. The service, the CLI and the metastore storage come in part 2b.

- **`Identity`** holds a process's chain, key and bundle.
  - Its validity comes from the leaf, and `renew_at` is two-thirds of the leaf's life (D2309).
  - `server_config` and `client_config` wrap `tls`.
  - `from_pem_files` reads the `tls.crt`/`tls.key`/`ca.crt` layout used by cert-manager and SPIRE (D2314).
  - `Debug` redacts the key.
- **`ca::Ca`**:
  - `init`: a P-256 root (10 years) and an intermediate (1 year, path length 0), returned as `CaMaterial` PEM. Its `Debug` redacts both keys.
  - `load`: needs only the intermediate's key.
  - `issue(csr, grant, serial, now)` signs a 24-hour leaf.

**R3.2 The CA builds every leaf from scratch.** From the CSR it copies only:
- the public key;
- the SPIFFE URI SANs, each of which must be in the `Grant` and in the CA's cluster;
- the DNS and IP SANs.

It never copies the CSR's CA bit, key usages, EKUs or validity. The test `a_csr_asking_to_be_a_ca_gets_a_plain_leaf` covers this.

**R3.3 Validity windows.** `notBefore` is backdated 5 minutes (`BACKDATE`) to absorb clock skew between nodes (§83 §15). Renewal is two-thirds of the whole window, backdate included.

**R3.4 Serials.** The CA reports the serial as the certificate encodes it: DER drops leading zero bytes. The deny list and `Identity::serial` compare these bytes.

- **`new_key_and_csr`** makes the key and CSR in the requester's memory (D2311). Only the CSR travels to the CA.
- **`token::JoinToken`**: `loamsjt1.<id>.<32-byte secret>`, URL-safe base64.
  - The CA stores only the secret's SHA-256, in a `TokenRecord`.
  - `TokenStore::redeem` checks the secret in constant time and spends the token in the same step.
  - A token lives one hour.
  - `MemoryTokens` is the test store. The metastore store comes in part 2b.
- **`DenyList`** revokes by serial or by SPIFFE ID (D2312).
- **API stability**: the crate-root re-exports are the API that design 85 (the desktop's QUIC streaming) and CT1 Task 6 build on. Changes are additive. Anything breaking needs a CT1 ruling.

Tests:
- `tests/ca.rs` (8): the join flow ending in mTLS over h3 and h2; the 24-hour and two-thirds schedule; a token used twice, an expired one and a wrong secret; grant, cluster and CSR refusals; a CSR asking for a CA certificate; the deny list by serial and by identity; keys never printed; PEM loading.
- Part 1's 8 tests also run.
- Clippy with `-D warnings` is clean.

## Part 2b (2026-10-30): the CA service, its storage and `loams ca`

The CA now runs as a service, behind the `loams` feature `transport` (off by default). Nothing calls it yet: CT1 Task 5 issues the compose tokens, and Task 6 puts the cluster listener on mTLS.

**R3.5 A crate for the CA service.** The service logic is a new crate, `crates/loams-ca` (`publish = false`). `crates/loams` only wires it in.
- The plan put the service in `crates/loams`. A separate crate keeps `loams-proto` and `connectrpc` out of `loams-transport`, which the desktop's transfer lane (design 85) depends on.
- It also lets the CA's tests run without building the server.

The crate has these parts:
- `doc::CaDoc`, the CA's state as one JSON document:
  - the root certificate, but never the root's key;
  - the intermediates, each with its key sealed;
  - the next serial;
  - the join tokens, stored as digests only;
  - the issued serials that are still live;
  - the deny list.
- `seal::KeySealer`, which seals keys with age to one X25519 key file. It follows D2205's `AgeSealer`, and it refuses an unsealed key.
- `store::CaDocStore`, a versioned compare-and-swap (CAS) store.
- `Authority`, which provides `init`, `create_token`, `revoke`, `rotate_intermediate`, `issue`, `renew`, `bundle`, `refresh_deny_list` and `status`.
- `connect`, the Connect `CertificateService` built over `Authority`.

**R3.6 Where the document lives.** It is kept the way the principal directory and the meter's documents are (`MetaDirectoryStore`): the metastore pointer `ca-state` in the system namespace points to a JSON object under `system/ca/state/` in the bucket.
- Each write loads the document, changes it, prunes it and saves it with a CAS. A write gives up after 16 lost races.
- A refused request writes nothing, so a CSR that is refused does not spend its token.
- A leaf signed in a losing attempt is thrown away and never returned.
- Pruning drops:
  - token records a day after they expire, so a second use still gets `join_token_spent` or `join_token_expired`;
  - issued serials once past `notAfter`;
  - revoked serials once their leaf has expired;
  - intermediates once past their retirement.

**R3.7 The sealing key file.** It is `LOAMS_CA_SEALING_KEY_FILE`, which defaults to `<data-dir>/ca/sealing.key`, mode 0600.
- Only `loams ca init` creates it. A node that serves the CA opens the existing file, because a key made on the spot could never open the sealed intermediate.
- A `meta` node without the file still serves `TrustBundle`. On that node, `Issue` and `Renew` answer `ca_not_initialized`.
- Every `meta` node needs a copy, as with the meter's key file.

**R3.8 Where it is served.** On `meta` nodes in cluster mode, on the cluster listener, next to the meter's internal routes.
- It is never served on a port with end-user authentication.
- Whether single-node modes (`dev`, `standalone`, compose) serve it is decided in Task 5, where compose services first join.

**R3.9 `Renew` and `VerifiedPeer`.** `Renew` reads a `loams_transport::VerifiedPeer` (the leaf's identities and its serial) from the request's extensions.
- Task 6's TLS layer inserts it. Until then, `Renew` answers `unauthenticated`.
- The CSR may ask only for identities the caller's certificate holds, never more.
- `Issue` also refuses a grant that holds a revoked identity, and `create_token` refuses to grant one.

**R3.10 The trust bundle.** `TrustBundleResponse` gains `intermediates` (field 2), following §83 §6.2 ("the root plus the active intermediates").
- `loams ca rotate intermediate --root-key-file` stops the old intermediate issuing at once and keeps it in the bundle for 30 days.
- The command refuses a root key that is not the root certificate's.

**R3.11 `loams ca` works on the stores, as `loams migrate` does** (`--data-dir`, `--meta`, `--bucket`).
- With the embedded metastore it runs with the engine stopped. With TiKV it can run at any time.
- An admin path for revoking on a running embedded stack comes with the mTLS listener (Task 6).
- `init` writes the root's key once, to a new file given by `--root-key-out` (mode 0600), for the deployment's secret store. It checks that path before it opens the stores. `--cluster` defaults to a new lowercase ULID, since no stack id exists yet; Task 5's `migrate` passes its own.
- `token --grant role/meta …` accepts short IDs in the CA's cluster. The token goes to stdout, or to `--out` (mode 0600).
- `revoke --node | --serial | --identity`.
- `status` prints JSON and warns 30 days before the root or the active intermediate expires.

**R3.12 Root rotation moves to Task 14.** The root lives 10 years, and cross-signing a new root with the old one only matters at that horizon. `loams ca rotate root` exits with 78 and points here.

**R3.13 Additive `loams-transport` API.** These additions are for this part and for Task 6:
- `TokenRecord::redeem`, so a store that keeps records elsewhere can check and spend a token in its own atomic update (`MemoryTokens` uses it);
- `DenyList::replace`;
- `Ca::new_intermediate`;
- `CaError::KeyMismatch` (a new variant; nothing matches `CaError` exhaustively);
- `VerifiedPeer` and `verified_peer`;
- `PeerError` re-exported at the crate root.

Nothing existing changed.

**Codegen.** `crates/loams-proto/build.rs` adds `ca.proto`, and the package is in `NOT_SDK_PACKAGES`, with a row in §44 §7.2's table. The Ruby and Kotlin descriptor sets are regenerated. The six reasons (`join_token_unknown`, `join_token_spent`, `join_token_expired`, `identity_not_granted`, `identity_revoked`, `ca_not_initialized`) are registered in `docs/api/reasons.md`.
